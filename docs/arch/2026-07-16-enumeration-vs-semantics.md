# 枚举规则 vs 开放语义：简历 Copilot 的事实治理原则

## 核心洞察

**枚举应该描述系统允许的状态，不应该描述现实世界可能出现的所有文本。**

拿"全国大学"这个例子：

```text
全国大学生创新创业大赛三等奖
```

LLM 从中提取出 `school = "全国大学"`，这不奇怪——LLM 确实会错。问题是系统的**检测层**用 regex 从源文本中也匹配到了 `全国大学`，然后判定为"已知实体，有证据支持"，于是 fabrication report 根本没有这条记录。

错误的匹配来自模式：

```python
r"[一-鿿]{2,40}(?:大学|学院|学校|…)"
```

`{2,40}` 太宽，"全国"（2字）+ "大学"（后缀）被当成学校实体，忽略后面紧跟的"生"字。

更泛化的问题是：**用字符串匹配去判断"这是什么实体"，是一个开放世界问题。枚举永远跟不上。**

---

## 合理枚举 vs 不合理枚举

### 合理枚举（系统内部状态，有限）

| 枚举 | 示例 | 理由 |
|------|------|------|
| Schema 类型 | `ExperienceType`, `OrganizationType` | 产品定义，有限状态 |
| 流程状态 | `FieldSupport.supported / unsupported / partial` | 系统内部协议 |
| 明确占位符 | `MISSING_PLACEHOLDERS = {"", "未提供", "未知"}` | 产品语义明确 |
| 确定性格式 | `EMAIL_PATTERN`, `PHONE_PATTERN` | 语法约束，封闭格式 |
| 业务约束 | `user_stage=="student" → 工作经验非必填` | 产品规则，非文本猜测 |

### 不合理枚举（用字符串猜测开放世界）

| 模式 | 例子 | 问题 |
|------|------|------|
| 后缀规则 | `company.endswith(("实验室", "研究院"))` | 无法区分正式机构名与场景描述 |
| 关键词黑名单 | `NOT_A_SCHOOL = {"全国大学", "大学生活动中心", …}` | 永远补不完 |
| 排除词表 | `if "大学生" in text: reject_school()` | 误伤"北京大学生物医学工程学院" |
| 类型字典 | `RESEARCH_ORG_KEYWORDS = {"实验室", "研究所", …}` | 依赖机构名称字符串而非事实证据 |

**所有拿"有限字符串枚举"去替代开放世界语义理解的规则，都不该成为核心判断。**

但枚举本身不是原罪。协议、状态、字段类型、确定性格式，很多地方就应该枚举。否则系统会自由发挥到连自己都不认识自己。

## 三层校验架构

```
第一层：提取
  LLM 从文本提取候选字段值
  → 可能出错（如"全国大学"被当作 school）

第二层：证据绑定（最关键）
  每个候选字段必须携带：
  {
    "field": "education.school",
    "value": "全国大学",
    "source_span": "全国大学生创新创业大赛三等奖",
    "source_section": "honors"
  }
  不保存 span 和 section 的判断是盲判。

第三层：类型校验
  判断：honors section 中的一段赛事名称 → education.school?
  答案：否

  理由不是"因为这个赛事名称不在黑名单里"，
  而是"source_section != education" + "source_span 是更长的奖项实体一部分"。
```

这不需要枚举：

```text
大学生创新创业大赛
数学建模竞赛
电子设计竞赛
大学生活动中心
```

只需要理解：

> **实体不能脱离来源 span 和 section。**

## 当前系统中应该保留的确定性 guard

| Guard | 合理性 | 说明 |
|-------|--------|------|
| `is_missing_placeholder()` | ✅ | 占位符语义明确 |
| 年份无 evidence → 清空 period | ✅ 但仅作负向过滤 | year 存在 ≠ period 正确 |
| FactLedger substring 校验 | 🟡 必要但不充分 | 只能回答"文本出现过"，不能回答"字段类型正确" |
| 学校 regex 后缀边界 `(?![一-鿿])` | ✅ 通用边界约束 | 不枚举具体词，只约束匹配终点 |
| Schema 字段定义 | ✅ 产品设计 | `experience_type`, `organization_type` 需要补 |

## 前几轮真正绕远的地方

就是不断试图把语义错误修成：

```text
新增一个字符串集合
新增一个后缀规则
新增一个例外
```

而不是转向：

```text
结构保留
字段 provenance
实体类型约束
LLM 判断
确定性 guard
```

不是"彻底不要规则"，而是：

> **不要用枚举规则承担它不擅长的事情：开放语义判断。**

否则最终会拥有三千行规则，仍然挡不住"全国大学生创新创业大赛"这种非常普通的句子。
